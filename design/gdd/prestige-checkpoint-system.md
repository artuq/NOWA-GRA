## Overview

Prestige/Checkpoint System to warstwa meta-progresji zbudowana na dwóch już w pełni zaprojektowanych podkomponentach: BurnoutSystem (wymuszona karta decyzji gdy Cringe utrzymuje się na 100 przez `BURNOUT_THRESHOLD` sekund, oferująca Accept-and-reset albo Defer-once — `design/quick-specs/final-burnout-2026-07-01.md`) i ChallengeSystem (opcjonalna warstwa trudności wybierana na starcie ery, wymieniająca gorsze mnożniki nagród akcji na większy mnożnik meta-bonusu — `design/quick-specs/challenge-era-runs-2026-07-01.md`). Realny nowy zakres TEGO GDD jest węższy niż te dwa podkomponenty: definiuje CZYM faktycznie jest jeden trwały META_BONUS z resetu ery i jak się stackuje, dokładną klasyfikację flag era-local vs meta-persistent od której zależy logika resetu każdego innego systemu, oraz API `DecisionCardSystem.inject_priority_card()` potrzebne zarówno BurnoutSystem jak i przyszłym mechanikom wymuszonych kart. Mechanicznie gracz odczuwa to jako nieuniknioną sufit swojego imperium: buduj, uderz w ścianę (widoczną przez ostrzegawczy countdown), i wybierz albo spieniężenie w świeżą erę z jednym trwałym zyskiem, albo kupienie kolejnej chwili czasu za realny koszt Morale. To Pillar 2 (decyzje mają pamięć) doprowadzony do strukturalnego wniosku — reset ery to nie porażka, to wypłata za wszystko co gracz po drodze wybrał.

## Detailed Design

### Core Rules

*Specialists not consulted — Lean mode (not a Section D/H HIGH-risk section). BurnoutSystem and ChallengeSystem mechanics below are locked by their own quick-specs and restated only in summary — those specs remain the source of truth for their internals; this GDD adds only what they explicitly deferred.*

**BurnoutSystem (locked, `final-burnout-2026-07-01.md`)**: trigger on `Cringe=100` sustained `BURNOUT_THRESHOLD` seconds → forced "Wypalenie" card via `inject_priority_card()` (Rule 6 below) → Accept (era reset + meta-bonus) or Defer-once (Morale cost). Not restated in full here.

**ChallengeSystem (locked, `challenge-era-runs-2026-07-01.md`)**: optional era-start difficulty picker, ratio-multiplier action penalties, produces `get_combined_meta_multiplier()` consumed by Rule 2 below. Not restated in full here.

1. **META_BONUS is path-typed** — when Choice A (Accept Burnout) resolves, the granted bonus's *type* is determined by `ClassPathSystem.get_active_path()` at that exact moment. If no path is active (nobody at Tier 1, or ambiguous per Class Path System F5), no meta-bonus is granted this cycle (see Edge Cases) — the run still resets, just without a permanent reward.

2. **META_BONUS magnitude formula** (see Formulas for the full derivation): scales with `ClassPathSystem.get_tier(active_path)` at burnout time and `ChallengeSystem.get_combined_meta_multiplier()`. A player who burns out at Tier 1 on a normal (no-challenge) run gets the smallest possible grant; a Tier 5 burnout under stacked challenges gets the largest.

3. **Each of the 4 paths grants a thematically distinct permanent bonus type**, extending that path's own tier-bonus flavor (Class Path System §Tier Bonuses by Path) into something that persists across the reset the tier bonuses themselves don't survive:

   | Path | Permanent meta-bonus type |
   |---|---|
   | `pato_streamer` | `META_REACH_MULT` — permanent multiplier on active-play Reach income |
   | `guru_celebryta` | `META_SPONSOR_MULT` — permanent multiplier on Sponsor income |
   | `ekspert_niszowy` | `META_HATERS_RESIST` — permanent reduction on Haters growth rate |
   | `biznesmen_contentu` | `META_SPONSOR_FLOOR` — permanent minimum Sponsor income floor (never drops to 0, even at era start) |

4. **Bonuses stack additively per type, across eras, uncapped in count but capped in magnitude** — burning out twice on `pato_streamer` in different eras adds a second `META_REACH_MULT` increment to the *same* running total (not two separate multipliers multiplying each other); burning out once on `pato_streamer` and once on `guru_celebryta` produces two independent permanent bonuses that both apply simultaneously. Each bonus type has its own `META_BONUS_MAX` ceiling (Tuning Knobs) — further grants of an already-capped type are absorbed with no effect (same "capped, not wasted-resource-refunded" pattern as Class Path's affiliation clamp).

4a. **Grant magnitude is blended (flat + tier-scaled), not pure tier scaling** *(revised per `/design-review`, 2026-07-13 — original pure-`tier_at_burnout` scaling mathematically punished path-switching, contradicting this Rule's own variety intent)* — F1's `tier_factor()` gives every burnout a flat baseline contribution plus a smaller-than-1:1 tier-scaled component, normalized so a Tier-5 grant is unchanged from the original formula (preserves all existing cap-safe high-tier worked examples) while a Tier-1 grant on an unfamiliar path is worth meaningfully more than before. Switching paths for variety still yields somewhat less than staying mastered — mastery is still rewarded — but no longer at the previous ~5:1 penalty ratio. See F1 for the exact formula.

4b. **First-ever accepted burnout *for each bonus type* gets a one-time bonus multiplier** *(rescoped from a single save-wide flag to per-type, `/design-review` 2026-07-13 re-review — the original global version permanently front-loaded the multiplier into whichever path the player happened to be on at their very first burnout, often before they understood the four paths' tradeoffs, creating an arbitrary and permanent type-vs-type imbalance)* — the first time a player accepts a burnout with a given path active, independently per type (a player who tries all four paths eventually gets this bonus four times, once per type, not once total), `FIRST_BURNOUT_BONUS_MULT` (Tuning Knobs) applies as an additional multiplicative factor on that type's grant, on top of 4a's blended tier factor. This exists specifically so a new player's first reset on any given path — the one that defines whether "payout, not failure" is believed — produces a bonus they can actually perceive, not just one that is mathematically nonzero. Tracked via four new meta-persistent flags `first_burnout_bonus_used[type]` (Core Rule 7) — each consumed exactly once, never again, even if a later burnout on that type would otherwise qualify (e.g. a save-migration edge case, see Edge Cases).

4b-i. **First-burnout grants are additionally ceilinged at `FIRST_BURNOUT_GRANT_CAP_FRACTION × META_BONUS_MAX[type]`** *(new, `/design-review` 2026-07-13 second re-review — adversarial systems-designer review found `first_burnout_factor` was excluded from the exponent's cap-safety proof: a first-ever grant at Tier 5 with even a modest 2-challenge stack can overshoot a type's entire lifetime cap by up to 2.42x in a single grant, silently one-shotting the "8-12 eras to cap" pacing target and defeating 4b's own perceptibility purpose by leaving nothing left to grant afterward)* — this ceiling applies **only** when `first_burnout_factor > 1.0` (i.e. only to the one first-ever grant per type); ordinary non-first grants are unaffected and keep their existing (already cap-safe per the `META_CHALLENGE_SCALING_EXPONENT` derivation) headroom, including the legitimate Tier-5/stacked-challenge case which can still land close to a type's full cap in one grant on its own merits. See F1 for the exact clamp.

4c. **A one-time "completionist" bonus rewards trying all four paths, independent of 4a/4b's per-grant math** *(new Core Rule, `/design-review` 2026-07-13 re-review — adversarial review found 4a/4b only soften the penalty for switching paths; they never make switching competitive with staying mastered, since `tier_factor(5)=5.0` is unchanged by construction. This rule adds a separate, additive lever that doesn't touch that ceiling.)* — the moment all four `META_BONUS_total[type]` running totals are simultaneously nonzero for the first time (i.e. the grant that makes the fourth distinct type go from `0.0` to `>0.0`, regardless of which type is last), each of the four types receives one additional flat increment of `BASE_INCREMENT[type] × VARIETY_BONUS_MULT` (Tuning Knobs), applied through F2's normal stacking-and-cap logic exactly like any other grant — an already-capped type simply absorbs it with no effect, same as always. This is the reward for exploration itself: a player who accepts at least one burnout on each of the four paths ends up with strictly more permanent progress, across all four tracks, than a player who never leaves their first path — a genuine incentive that doesn't depend on any single grant's tier math. Tracked via the new meta-persistent flag `variety_bonus_used` (Core Rule 7) — consumed exactly once, ever, per save. Does not replace or interact with 4a's blended tier scaling or 4b's per-type first-burnout multiplier — it is a third, independent additive lever alongside them (see F1b).

5. **META_BONUSes are permanent from the moment they're granted** — they are never reduced, reset, or removed by any future era transition. This is the one piece of state in the entire game that survives every reset; everything else (Class Path affiliation, era-local flags, active Challenges) resets to zero each time. **Cap-lowering migration policy** *(added `/design-review` 2026-07-13 second re-review — economy-designer flagged permanent+unvalidated caps with no defined migration path as a tuning trap)*: this Rule already resolves the case where a future balance pass lowers a `META_BONUS_MAX[type]` value below totals some players have already reached — those totals are simply preserved unchanged (never reduced, per this Rule) and no further grants apply to that type until/unless the cap is raised again. No new save-migration mechanism is needed; this is stated explicitly here so it isn't rediscovered as an open question during a future retune.

6. **`DecisionCardSystem.inject_priority_card(card_id: StringName)` (new API)** — bypasses the normal card pool, weighting, and cooldown entirely; presents the given card on the next available frame; blocks all normal card presentation until resolved (`_card_pending`-style guard, mirroring BurnoutSystem's own flag). This is a general-purpose injection path, not Burnout-specific — any future forced-card mechanic reuses this same API rather than inventing its own.

7. **Flag classification (the blocking gap both quick-specs deferred to this GDD)**:
   - **Era-local** (cleared on every `era_transitioned`): all 5 resources, all Class Path affiliation/tier state, all Class Path path-tagged card counters, all active Challenge flags, `BurnoutSystem._deferred_this_era`.
   - **Meta-persistent** (never cleared): `era_count`, all granted META_BONUS values (by type), Class Path's `best_tier_reached[path]` / `eras_spent_as[path]`, all `burnout_accepted_era_N` / `burnout_deferred_era_N` milestone flags, `first_burnout_bonus_used[type]` (four flags, one per bonus type) *(added per `/design-review`, 2026-07-13 — Core Rule 4b; rescoped from a single global flag to per-type in the 2026-07-13 re-review)*, `variety_bonus_used` *(new, 2026-07-13 re-review — Core Rule 4c)*.
   - This classification is the canonical answer other systems' GDDs deferred to this one — Class Path System's Era Reset section and BurnoutSystem's own spec both point here.

### States and Transitions

**Era lifecycle** (extends BurnoutSystem's own state machine with the meta-bonus grant step):

| State | Description | Transition |
|---|---|---|
| `active_era` | Normal play, Challenges (if any) applied, Class Path progressing | → `burnout_warning` when Cringe sustains near threshold (BurnoutSystem) |
| `burnout_warning` | Countdown visible, no interruption to play | → `burnout_card_presented` at full threshold, or back to `active_era` if Cringe drops |
| `burnout_card_presented` | Forced card blocking normal play | → `era_transitioning` on Choice A, → `active_era` (deferred) on Choice B |
| `era_transitioning` | **New state this GDD adds** — the ordering window between Choice A confirming and the new era's first frame: (1) `PrestigeSystem` calls `ClassPathSystem.get_active_path()`/`get_tier()` directly (see ordering contract below); (2) `PrestigeSystem` calls `ClassPathSystem.reset_era_state()`; (3) meta-bonus is computed (F1/F2) and granted; (4) era-local flags clear (Rule 7); (5) `SaveSystem.save_now()` persists the fully-transitioned state, then `SaveSystem.resume_autosave()` *(reordered per `/design-review`, 2026-07-13 second re-review — see atomicity note below)*; (6) `era_transitioned` signal fires; (7) `ChallengeSystem` shows the Challenge Selection screen, itself autosaved normally as a separate, later event once confirmed | → `active_era` once Challenge Selection is confirmed (or immediately if the player has no challenges available yet) |

**Critical ordering note**: Rule 1's "path active at burnout time" read MUST happen before Class Path's `reset_era_state()` clears the affiliation/tier state it depends on. `PrestigeSystem` (new Autoload) is the one that calls `ClassPathSystem.get_active_path()`/`get_tier()` and *then* triggers the reset sequence — it does not passively listen to `era_transitioned` for this read, because by the time that signal fires (per Class Path's own spec), the state is already cleared. `PrestigeSystem` owns the orchestration order of Choice A's resolution; `era_transitioned` is emitted only after `PrestigeSystem` has done its meta-bonus read.

**Call-contract lock *(revised per `/design-review`, 2026-07-13 — this was previously ambiguous between a direct call and a signal round-trip, a real ordering-bug risk in a signal-heavy codebase)***: the read-then-reset sequence (`get_active_path()` → `get_tier()` → `reset_era_state()`, all three) MUST be a direct synchronous method-call chain made by `PrestigeSystem` on `ClassPathSystem`'s reference — **never** a signal emission awaiting a listener. If `reset_era_state()` is ever refactored to run via a signal instead, that signal's connection from `PrestigeSystem` MUST NOT use `CONNECT_DEFERRED` (or any `call_deferred` in the chain) — a deferred connection breaks the same-frame ordering guarantee silently, with no compile-time signal that anything is wrong. **None of the three chained methods may contain an `await`, anywhere in their implementation** *(added per `/design-review`, 2026-07-13 second re-review — godot-specialist review found `CONNECT_DEFERRED`/`call_deferred` were the only leaks named, but a plain GDScript `await` inside any of `get_active_path()`, `get_tier()`, or `reset_era_state()` yields control and resumes later exactly like a deferred call, breaking the same-frame guarantee just as silently and without tripping the stated rule)*. This constraint is binding on the implementation, not a suggestion.

**Autoload initialization-order contract** *(added per `/design-review`, 2026-07-13 second re-review — godot-specialist review found this unstated)*: `PrestigeSystem` calls into `ClassPathSystem`, `DecisionCardSystem`, `SaveSystem`, and `HistoryFlagManager` at runtime, all presumed Autoloads. No autoload's `_ready()` may depend on any other autoload named here having already completed its own `_ready()` — every cross-autoload call this GDD specifies happens in response to a runtime event (Choice A confirmation), never during another autoload's initialization. If a future implementation needs setup-time coordination between these autoloads, that ordering must be made explicit in `project.godot`'s autoload list and documented in an ADR — it is out of scope for this GDD to assume or resolve.

### Interactions with Other Systems

- **Class Path System** (hard, read then triggers reset) — `PrestigeSystem` reads `get_active_path()`/`get_tier()` at the moment Choice A resolves (before reset), then calls `ClassPathSystem.reset_era_state()` **directly** (no signal round-trip — see States and Transitions' call-contract lock). Also reads `best_tier_reached[path]`/`eras_spent_as[path]` meta-flags, though those are informational/UI (e.g. an era-summary screen) rather than inputs to the magnitude formula itself (see Formulas — magnitude uses the *at-burnout* tier, not the lifetime-best tier, to keep the incentive tied to "how far did you push THIS era," not a one-time lifetime max).
- **Decision Card System** (hard, new API) — `inject_priority_card()` (Rule 6) is a new method this GDD requires; BurnoutSystem's forced card and any future forced-card mechanic depend on it existing. The FSM sits in a `priority_card_pending` state orthogonal to the normal `cooldown → checking → presenting → resolving` cycle: while pending, normal presentation is blocked but `checking`'s cooldown-action-counting continues to accumulate as usual (so a normal card is immediately eligible the moment the priority card resolves, rather than needing to re-accumulate cooldown from zero).
- **History Flag Manager** (hard, read+write) — owns the flag classification sweep (Rule 7); `PrestigeSystem` is the system that knows which flags belong to which bucket, but the actual clear/preserve mechanics run through HistoryFlagManager's existing API.
- **Challenge System** (hard, read) — `get_combined_meta_multiplier()` scales the magnitude formula (Rule 2/Formulas).
- **Resource Manager** (hard, write) — era-start reset writes the 5 default values (already specified in `final-burnout-2026-07-01.md` §4.2); META_BONUS effects apply as ongoing multipliers/floors at the point resources are computed each era, not as one-time grants.
- **Action System** (soft, read) — `META_REACH_MULT`/`META_SPONSOR_MULT` apply at action-reward resolution, alongside Class Path's own active-path multiplier and Challenge modifiers (three independent multiplicative layers — see Formulas for stacking order).
- **Save/Persistence System** (hard, read+write) — `era_count`, all META_BONUS values by type, and the meta-persistent flag set are part of the serialize/restore cycle. **⚠️ New requirement, `/design-review` 2026-07-13**: `save-persistence-system.md` documents autosave firing on card-resolution events (2s debounce) — Choice A's resolution IS a card resolution, so an unmodified autosave trigger can fire *inside* the `era_transitioning` window and violate this GDD's atomicity contract (Edge Cases). `PrestigeSystem` MUST call `SaveSystem.suppress_autosave()` on entering `era_transitioning` and `SaveSystem.resume_autosave()` immediately after `SaveSystem.save_now()` completes. **`suppress_autosave()`/`resume_autosave()` do not exist yet** — this is a new API this GDD requires of Save/Persistence System, same pattern as `inject_priority_card()` on Decision Card System; `save-persistence-system.md` needs a corresponding update (tracked in Open Questions).
  **⚠️ Suppression window narrowed, `/design-review` 2026-07-13 second re-review** — godot-specialist review found the original contract suppressed autosave across the *entire* sequence including the Challenge Selection screen (step 7), which blocks on arbitrary player confirmation time; on mobile, an OS-initiated background-kill during that unbounded wait would lose everything since the pre-burnout save, a larger data-loss window than the ordering race being fixed. **Fix**: `SaveSystem.resume_autosave()` now runs immediately after `save_now()` at the end of step 5 (era-flip fully committed: meta-bonus granted, flags swept) — **before** `era_transitioned` fires and before Challenge Selection ever opens (step 7). The suppression window is now just steps 1-5 (all synchronous, same-frame), not the player-paced Challenge Selection step. Challenge Selection's own confirmation is autosaved normally afterward like any other event; if interrupted, Edge Cases' existing "zero-challenge is a safe default" restore behavior already covers it — no new machinery needed for that part.

## Formulas

*Specialist consulted: `systems-designer` — Section D is HIGH-risk, consulted even in Lean mode.*

META_BONUS magnitude is computed once per accepted burnout from two already-locked inputs (`ClassPathSystem.get_tier(active_path)` at burnout time, `ChallengeSystem.get_combined_meta_multiplier()`), added to a per-type running total that is capped and never reduced (Core Rules 4/5), then consumed at four distinct resolution points — one per bonus type — because the four types are not mechanically equivalent (two are reward-resolution multipliers, one is a growth-rate resistance, one is a one-time era-start floor). F3's sub-formulas are written as *extensions* of already-locked formulas (Challenge spec's `final_reach = base_reach × Mult(M) × challenge_modifier`, Resource System's `H_rate(C)`) — they insert new factors into existing pipelines rather than redefining them.

### F1. META_BONUS Grant Magnitude

*Revised per `/design-review`, 2026-07-13 — the original pure `tier_at_burnout` scaling made switching Class Paths for variety mathematically worse than staying mastered on one path (an inverted incentive vs. Core Rule 3's intent), and its Tier-1 baseline output (2%) was imperceptible against losing 100% of era-local progress. `tier_factor()` and `first_burnout_factor` below address both without touching the previously-verified Tier-5/stacked-challenge ceiling (unchanged, still cap-safe — see worked examples).*

`raw_increment[type] = BASE_INCREMENT[type] × tier_factor(tier_at_burnout) × (combined_meta_multiplier)^META_CHALLENGE_SCALING_EXPONENT × first_burnout_factor`

`bonus_increment[type] = raw_increment[type]` if `first_burnout_factor == 1.0`; else `min(raw_increment[type], FIRST_BURNOUT_GRANT_CAP_FRACTION × META_BONUS_MAX[type])` *(Core Rule 4b-i — the ceiling applies only to the one first-ever grant per type, never to ordinary repeat grants)*

`tier_factor(tier) = (TIER_FLAT_BASE + tier) × 5 / (TIER_FLAT_BASE + 5)`

| Symbol | Type | Range | Description |
|---|---|---|---|
| `type` | enum | `{META_REACH_MULT, META_SPONSOR_MULT, META_HATERS_RESIST, META_SPONSOR_FLOOR}` | Bonus type, resolved by `ClassPathSystem.get_active_path()` at Choice A (Core Rules 1/3) |
| `tier_at_burnout` | int | 1–5 | `ClassPathSystem.get_tier(active_path)`, read at the moment Choice A resolves, before `reset_era_state()` (States and Transitions ordering) |
| `TIER_FLAT_BASE` | float (tuning knob) | 0–4, default **2** | Flat component blended into the tier scaling (Core Rule 4a). The `5/(TIER_FLAT_BASE+5)` normalization is fixed (not separately tunable) so `tier_factor(5) = 5` always — identical to the original formula's Tier-5 output, preserving every existing Tier-5 worked example and cap relationship. Raising `TIER_FLAT_BASE` compresses the low-tier/high-tier ratio further (more variety-friendly, less mastery-differentiated); `0` reduces to the original pure-tier formula |
| `tier_factor(tier_at_burnout)` | float | `[15/7 ≈ 2.143, 5.0]` at default `TIER_FLAT_BASE=2` | Blended tier contribution — see table below for all 5 tier values at the default |
| `combined_meta_multiplier` | float | `{1.0} ∪ [1.8, ~15]` at current Challenge catalogue + `CHALLENGE_MAX_ACTIVE=3` *(floor corrected per `/design-review`, 2026-07-13 — the real single-challenge floor in `challenge-era-runs-2026-07-01.md`'s locked catalogue is 1.8, not 1.5; 1.5 was only reachable via a `balance.json` retune, not "at current catalogue" as originally stated)* | `ChallengeSystem.get_combined_meta_multiplier()`, read at the same moment; 1.0 if no challenges active |
| `BASE_INCREMENT[type]` | float (tuning knob, per-type array) | see table below | Base grant per tier-point, before challenge scaling |
| `META_CHALLENGE_SCALING_EXPONENT` | float (tuning knob) | 0.3–0.5, default **0.5** *(range narrowed from 0.3–1.0, `/design-review` 2026-07-13 re-review — at 1.0 a single Tier-5/max-challenge-stack burnout could overshoot a type's cap by 3–9x in one grant, silently breaking the "8–12 eras to cap" pacing target; 0.5 is the highest exponent at which a single non-first-burnout grant, at any type's worst-case inputs, still stays within that type's own cap — `META_SPONSOR_MULT` is the tightest, safe up to ≈0.51 — see Tuning Knobs)* | Dampens `combined_meta_multiplier`'s contribution. `0.5` (locked default, now also the range ceiling) = square-root — rewards challenge-stacking clearly without letting one cycle dominate the multi-era stacking arc (Core Rule 4), and is the mathematically safe ceiling for single-grant cap-safety |
| `first_burnout_factor` | float | `{1.0, FIRST_BURNOUT_BONUS_MULT}` | `FIRST_BURNOUT_BONUS_MULT` (Core Rule 4b, Tuning Knobs) if `first_burnout_bonus_used[type] == false` for this grant's type and the grant is nonzero; `1.0` for every subsequent burnout on that type. Consumes that type's flag on use, never the others *(rescoped per-type, `/design-review` 2026-07-13 re-review)* |
| `FIRST_BURNOUT_GRANT_CAP_FRACTION` | float (tuning knob) | 0.3–0.6, default **0.5** *(new, `/design-review` 2026-07-13 second re-review — Core Rule 4b-i)* | Ceilings a first-ever grant (only) at this fraction of `META_BONUS_MAX[type]`, so `first_burnout_factor` can never one-shot a type's entire lifetime cap regardless of tier/challenge stacking |
| `raw_increment[type]` | float | `> 0` | Pre-ceiling computed value, before the 4b-i first-burnout clamp |
| `bonus_increment[type]` | float | `> 0` (grant only fires when a path is active, i.e. `tier_at_burnout ≥ 1`, per Core Rule 1) | Amount added to the type's running total this cycle, before F2's cap — equals `raw_increment[type]` for non-first grants, or the 4b-i-clamped value for first grants |

**`tier_factor(tier)` at default `TIER_FLAT_BASE=2`:**

| `tier_at_burnout` | `tier_factor` | vs. original pure-tier value |
|---|---|---|
| 1 | 2.143 | was 1 (+114%) |
| 2 | 2.857 | was 2 (+43%) |
| 3 | 3.571 | was 3 (+19%) |
| 4 | 4.286 | was 4 (+7%) |

**`BASE_INCREMENT[type]` (proposed defaults):**

| Type | `BASE_INCREMENT` | Units |
|---|---|---|
| `META_REACH_MULT` | 0.02 | fractional multiplier (2% per unit) |
| `META_SPONSOR_MULT` | 0.025 | fractional multiplier (2.5% per unit) |
| `META_HATERS_RESIST` | 0.015 | fractional reduction (1.5% per unit) |
| `META_SPONSOR_FLOOR` | 3.0 | flat Sponsors |

**Output range**: `> 0`, unbounded above at the formula level (bounded in practice by the Challenge catalogue's max stackable multiplier and `CHALLENGE_MAX_ACTIVE`). Not itself capped — F2 applies the hard per-type ceiling.

**Worked example (Tier 1, no challenge, player's first-ever accepted burnout on `META_REACH_MULT`, i.e. `pato_streamer` — "small becomes real")**: `META_REACH_MULT`, `tier=1` → `tier_factor=2.143`, `multiplier=1.0`, `first_burnout_factor=2.5` → `0.02 × 2.143 × 1.0^0.5 × 2.5 = 0.1071` (10.7%) — a first-time player can see this land.
**Worked example (Tier 1, no challenge, a later `pato_streamer` burnout — not that type's first)**: same inputs, `first_burnout_factor=1.0` → `0.02 × 2.143 × 1.0 × 1.0 = 0.0429` (4.3%) — still meaningfully above the original formula's 2%, without needing the one-time bonus.
**Worked example (Tier 3, one challenge, not the first)**: `tier=3` → `tier_factor=3.571`, `multiplier=2.0` → `0.02 × 3.571 × 1.414 × 1.0 = 0.1010` (10.1%).
**Worked example (Tier 5, stacked challenges, not the first — "meaningful, clearly larger")**: `bez_tlumu` (3.0) × `drama_bez_granic` (2.5) × `wypalony_ale_core` (2.0) = 15.0. `tier=5` → `tier_factor=5.0` (unchanged from the original formula) → `0.02 × 5.0 × 15.0^0.5 × 1.0 = 0.02 × 5 × 3.873 = 0.3873` (38.7%) — identical output to the pre-revision formula; this worked example, and its cap-safety, are unaffected by the revision (4b-i's ceiling only applies to first-ever grants, and this one isn't).
**Worked example (Tier 5, stacked challenges, first-ever burnout on `META_SPONSOR_MULT` — 4b-i ceiling triggers)**: same `combined_meta_multiplier=15.0`, `tier=5` → `tier_factor=5.0`, `first_burnout_factor=2.5` → `raw_increment = 0.025 × 5.0 × 15.0^0.5 × 2.5 = 1.209` (120.9%) — without 4b-i this would consume the entire `META_SPONSOR_MULT` cap (0.50) and then some in a single grant. 4b-i clamps it: `FIRST_BURNOUT_GRANT_CAP_FRACTION (0.5) × META_BONUS_MAX[META_SPONSOR_MULT] (0.50) = 0.25` → `bonus_increment = min(1.209, 0.25) = 0.25` (25%) — still a large, clearly perceptible first payout, but no longer capable of exhausting the type's entire multi-era arc in one cycle.

### F1b. Variety Completionist Bonus (Core Rule 4c)

`variety_grant[type] = BASE_INCREMENT[type] × VARIETY_BONUS_MULT` for all four types simultaneously, applied once via F2's normal `min(total + grant, cap)` logic.

Fires exactly once per save, at the moment the fourth distinct `META_BONUS_total[type]` transitions from `0.0` to `>0.0` (i.e. immediately after whichever burnout's F1/F2 grant is the one that makes all four types nonzero for the first time) — checked as a side-effect of every accepted-burnout grant, not a separate trigger the player takes an action for.

| Symbol | Type | Range | Description |
|---|---|---|---|
| `VARIETY_BONUS_MULT` | float (tuning knob) | 1.0–4.0, default **2.0** | Multiplies `BASE_INCREMENT[type]` to produce each type's flat completionist grant. Mirrors `FIRST_BURNOUT_BONUS_MULT`'s knob shape (Core Rule 4b) |
| `variety_grant[type]` | float | `> 0` | Added to each of the four running totals via F2, same cap/absorption rules as any other grant |

**Worked example**: a player has already banked `META_REACH_MULT=0.20`, `META_SPONSOR_MULT=0.15`, `META_HATERS_RESIST=0.10` from three prior burnouts on three different paths (all nonzero), and has never accepted a burnout on `biznesmen_contentu` (so `META_SPONSOR_FLOOR=0.0`). Their next burnout happens on `biznesmen_contentu`, Tier 2, no challenge, not that type's first burnout → F1 grants `3.0 × 2.857 × 1.0 × 1.0 = 8.57` to `META_SPONSOR_FLOOR` via the normal path (now `8.57`, nonzero — all four types are nonzero for the first time). F1b fires once: each type additionally receives `BASE_INCREMENT[type] × 2.0` — `META_REACH_MULT += 0.04` (→`0.24`), `META_SPONSOR_MULT += 0.05` (→`0.20`), `META_HATERS_RESIST += 0.03` (→`0.13`), `META_SPONSOR_FLOOR += 6.0` (→`14.57`). `variety_bonus_used` is set `true` and never fires again.

### F2. Per-Type Running Total (Stacking + Cap)

`META_BONUS_total[type] = min( META_BONUS_total_prev[type] + bonus_increment[type], META_BONUS_MAX[type] )`

| Symbol | Type | Range | Description |
|---|---|---|---|
| `META_BONUS_total_prev[type]` | float | `[0.0, META_BONUS_MAX[type]]` | Running total before this grant — permanent, never reduced (Core Rule 5) |
| `bonus_increment[type]` | float | `> 0` (F1 output) | This cycle's grant |
| `META_BONUS_MAX[type]` | float (tuning knob, per-type) | see table below | Hard ceiling. Grants past the cap are absorbed with **no effect** (same pattern as Class Path's `CARD_CONTRIBUTION_MAX` clamp) |
| `META_BONUS_total[type]` | float | `[0.0, META_BONUS_MAX[type]]` | Canonical stored value, read by F3 |

**`META_BONUS_MAX[type]` (proposed defaults, deliberately non-uniform):**

| Type | Cap | Units | Rationale |
|---|---|---|---|
| `META_REACH_MULT` | 0.50 (50%) | fractional multiplier | Reach is the primary currency; permanent ceiling roughly matching one strong Class Path T1 bonus (+30%) is proportionate for something earned over many eras |
| `META_SPONSOR_MULT` | 0.50 (50%) *(lowered from 0.60, `/design-review` 2026-07-13)* | fractional multiplier | **Was 0.60**, rationalized by "Sponsors has no consumption sink, so inflated income carries less risk" — economy review flagged this as backwards: a resource with no sink is exactly where a *permanent, never-revocable* multiplier (Core Rule 5) does the most damage, since nothing ever drains the inflated total back down. Capped at parity with `META_REACH_MULT` — **but economy-designer review (second re-review) found the cap number itself doesn't resolve the underlying problem**: any permanent addition into a zero-sink resource compounds unboundedly regardless of the ceiling chosen. See the explicit scope decision below. |
| `META_HATERS_RESIST` | 0.40 (40%) | fractional reduction | Deliberately well below 100% — must never fully stop Haters growth (extends DDR-0001 #2's "never zero a core resource flow" principle by analogy — confirmed as intentional extension, not automatic restatement) |
| `META_SPONSOR_FLOOR` | 100.0 | flat Sponsors | Meaningful but bounded head start; same zero-sink risk as `META_SPONSOR_MULT` above, same explicit scope decision applies |

**Zero-sink Sponsor scope decision *(locked, `/design-review` 2026-07-13 second re-review)*** — `META_SPONSOR_MULT` and `META_SPONSOR_FLOOR` both feed Sponsors, which Team/Staff Management (systems-index #15, Not Started) will eventually give a consumption sink, but doesn't have one today. Two options were weighed: (a) gate both bonus types off entirely until the sink ships, or (b) accept sinkless Sponsor inflation as a known, time-boxed Vertical Slice state. **Decision: (b)** — both types ship as designed for Vertical Slice; capping the numbers (as this revision already did for `META_SPONSOR_MULT`) bounds the *rate* of inflation to something manageable at VS scale even without a sink, and gating them entirely would remove two of the four path identities' payoffs for a problem that doesn't bite until many eras of accumulated play. **RESOLVED 2026-07-22**: `design/gdd/team-staff-management.md` designed — its `hire_cost()` formula (unbounded, geometrically escalating per hire) is the missing per-era Sponsors consumption sink. Both `META_BONUS_MAX[META_SPONSOR_MULT]` and `META_BONUS_MAX[META_SPONSOR_FLOOR]` were re-examined against this sink and remain unchanged (0.50 / 100.0) — the sink addresses live-session flow accumulation directly; the permanent running totals were already bounded by F2's cap independent of any sink.

**Output range**: `[0.0, META_BONUS_MAX[type]]`, monotonically non-decreasing across the game's lifetime — never cleared by era reset (Core Rule 5).

**Worked example**: `META_REACH_MULT` from `0.0`: player's first-ever accepted burnout, Tier-1, no challenge → `+0.1071` (F1's first-burnout example) → total `0.1071`. A later Tier-5-stacked-challenge grant (`+0.3873`) → `0.4944`. A third grant, Tier-3/one-challenge (`+0.1010`) → computes `0.5954` → clamped to `0.50`; `0.0954` absorbed with no effect.

### F3. Final Reward Stacking

**General principle**: each contributing system computes exactly **one** factor via its own internal combination rule (Class Path tier bonuses: additive within Class Path; Challenge modifiers: multiplicative within Challenge; META_BONUS: additive within type per F2). These system-level factors combine **multiplicatively across systems** at the resource's resolution point. Rationale: keeps each layer independently visible/auditable (each panel shows its own number); avoids additive cross-blending with sub-1.0 Challenge nerfs (risk of negative/non-monotonic totals); product of independently-capped factors stays bounded — Pillar 1's "fair predictable math" without uncontrolled compounding. All rounding (round-half-up, per `action_ui_number_format`) happens **once**, at the end of the full product, never per layer.

#### F3a. Reach Reward Stacking (active-play only)

`final_reach(action_id) = max( 1, round_half_up( base_reach(action_id) × Mult(M) × class_path_multiplier(action_id) × challenge_modifier(action_id) × (1 + META_REACH_MULT_total) ) )`

*`max(1, ...)` floor added per `/design-review`, 2026-07-13 — see Edge Cases: a hard Morale band + a low-base action + a near-floor `challenge_modifier` + zero accrued `META_REACH_MULT` (realistic for an early-era player who stacks a hard challenge before their first grant) could otherwise round to 0 Reach for a completed action, an unhandled zero-reward case. Extends `META_HATERS_RESIST`'s existing "never fully zero a core resource flow" principle (DDR-0001 #2) to this pipeline.*

| Symbol | Type | Range | Description |
|---|---|---|---|
| `base_reach(action_id)` | float | per `action_zasiegi_base` (5/10/6) | Locked, Action System |
| `Mult(M)` | float | `{0.50, 0.75, 0.90, 1.00}` | Locked, Resource System (Morale band) |
| `class_path_multiplier(action_id)` | float | `≥ 1.0` *(corrected per `/design-review`, 2026-07-13 — `class-path-system.md`'s `get_active_multiplier()` guarantees a floor of 1.0, never 0, whether or not a path is active or has a bonus at the current tier; the original `≥ 0` invited an implementer to treat 0 as valid, which the source API never returns)* | `ClassPathSystem.get_active_multiplier(action_id)` — existing API, opaque input, not redefined here |
| `challenge_modifier(action_id)` | float | `[0.05, unbounded)` (floor: `CHALLENGE_MODIFIER_FLOOR`) | ChallengeSystem's product of active modifiers, opaque input |
| `META_REACH_MULT_total` | float | `[0.0, 0.50]` (F2 output) | This GDD's new contribution |
| `final_reach(action_id)` | int | `≥ 1` *(was `≥ 0` — see `max(1, ...)` floor above)* | Reach granted on action completion |

**Worked example (no challenge)**: `zrob_drame`, base 10, `Mult=1.00`, path `1.30` (pato T1), challenge `1.0`, meta `0.3873` → `10 × 1.00 × 1.30 × 1.0 × 1.3873 = 18.03` → **18 Reach** (vs. 13 with Class Path alone).
**Worked example (all four layers)**: same action, `Mult=0.90`, path `1.30`, challenge `0.5` (`bez_tlumu`), meta `0.0429` (F1's "later Tier-1 burnout" example, replacing the no-longer-reachable `0.02`) → `10 × 0.90 × 1.30 × 0.5 × 1.0429 = 6.101` → **6 Reach**.
**Worked example (floor triggers)**: a base-`5` action, `Mult=0.50` (hard Morale band), path `1.0` (no path bonus this tier), challenge `0.05` (`CHALLENGE_MODIFIER_FLOOR`, an extreme stacked-hard-challenge run), meta `0.0` (no grant yet) → `5 × 0.50 × 1.0 × 0.05 × 1.0 = 0.125` → rounds to `0`, floored to **1 Reach**.

#### F3b. Sponsor Income Stacking (active-play only, card-resolution scoped)

`final_sponsors = round_half_up( base_sponsors_roll × class_path_sponsor_multiplier × (1 + META_SPONSOR_MULT_total) )`

| Symbol | Type | Range | Description |
|---|---|---|---|
| `base_sponsors_roll` | int | 1–3 | Existing `sponsorzy_per_qualifying_card` random roll |
| `class_path_sponsor_multiplier` | float | thematically ≥ 1.0 | Class Path guru/biznesmen Sponsor tier bonuses — **⚠️ no resolution API defined yet, see Open Questions** |
| `META_SPONSOR_MULT_total` | float | `[0.0, 0.50]` (F2 output) *(cap lowered from 0.60, see F2)* | This GDD's new contribution |
| `final_sponsors` | int | ≥ 0 | Sponsors granted on qualifying-card resolution |

No `challenge_modifier` factor — the current Challenge catalogue defines no sponsor axis; if added later it slots in per F3a's pattern.

**Worked example (endgame)**: roll 3, guru T1 `1.20`, meta capped `0.50` → `round(3 × 1.20 × 1.50) = round(5.4)` → **5 Sponsors** (vs. 4 with Class Path alone).

#### F3c. Haters Growth Rate Resistance — applies online AND offline (locked decision, 2026-07-12)

`H_rate_final(C) = H_rate(C) × (1 − META_HATERS_RESIST_total)`

| Symbol | Type | Range | Description |
|---|---|---|---|
| `H_rate(C)` | float | per Resource System's locked formula | Existing, unmodified |
| `META_HATERS_RESIST_total` | float | `[0.0, 0.40]` (F2 output) | This GDD's new contribution |
| `H_rate_final(C)` | float | `[0.60 × H_rate(C), H_rate(C)]` | Effective Haters growth rate |

**Scope (locked)**: unlike Class Path multipliers and Challenge modifiers (both active-play-only by their own rules), this resistance applies to **both active-play and offline** Haters growth. Rationale: those systems are era-local and per-action (complex for offline sim — Pillar 4 demands offline simplicity); META_HATERS_RESIST is meta-persistent and a single flat rate factor — simpler than anything the offline sim already computes, fully transparent in the offline report. Side benefit, explicitly intended: this is the game's one lever that softens the known offline Morale-drain spiral (Haters growth → `M_drain(N)`), giving `ekspert_niszowy` burnouts a distinctly "calmer offline" long-term identity.

**Worked example**: `C=80` → `H_rate = 0.02 + 0.8² × 1.0 = 0.66`. With `META_HATERS_RESIST_total = 0.30`: `0.66 × 0.70 = 0.462` Haters/min (~30% slower).

`sponsors_at_era_start = max( 0.0, META_SPONSOR_FLOOR_total )`

Overrides Final Burnout's default era-start reset (`Sponsors = 0`, `final-burnout-2026-07-01.md` §4.2) for this one resource only. Applied once, at the exact moment `era_transitioning`'s resource-reset step writes Sponsors — not an ongoing rate.

| Symbol | Type | Range | Description |
|---|---|---|---|
| `META_SPONSOR_FLOOR_total` | float | `[0.0, 100.0]` (F2 output) | This GDD's new contribution |
| `sponsors_at_era_start` | float | `[0.0, 100.0]` | Sponsors value written at era-start reset, replacing the flat 0 default |

**Worked example**: total `9.0` (three Tier-1 grants across three eras) → new era starts with `Sponsors = 9` instead of `0`.

## Edge Cases

*Specialist not consulted — Lean mode (not a Section D/H HIGH-risk section).*

- **If Choice A (Accept Burnout) resolves with no active path** (nobody at Tier 1, or ambiguous per Class Path F5): no META_BONUS is granted this cycle. The era still resets normally — reset is never blocked by the absence of a reward. **The Wypalenie card's presentation MUST surface this before the player confirms** ("No active path — this burnout grants no permanent bonus") *(revised per `/design-review`, 2026-07-13 — was a non-blocking "SHOULD," which meant this warning could ship absent; it is now a locked requirement, not a writer-optional nicety, since a silent zero-reward burnout directly contradicts Player Fantasy's "nothing is done to the player without consent")* — exact copy remains a writer task, but the presence of *some* explicit warning at this exact moment is not optional.
- **If a burnout is accepted with no active path AND it would have been the player's first-ever accepted burnout on any type**: none of the four `first_burnout_bonus_used[type]` flags is consumed — no bonus was computed, so there is nothing to spend any one-time multiplier on. Each flag stays `false` until that specific type's first burnout that actually has an active path and produces a grant *(rescoped per-type, `/design-review` 2026-07-13 re-review)*.
- **If all four META_BONUS types are at their caps**: further burnouts grant nothing (absorbed per F2), but the burnout mechanic itself is unchanged — the card still fires, Defer still costs Morale, the era still resets. No softlock: the trigger is Cringe-driven, not reward-driven.
- **If the app is killed mid-transition, before `save_now()` completes** (after Choice A confirmed, during meta-bonus read+grant → resource reset → flag sweep, i.e. States and Transitions' steps 1-5): this portion — and only this portion — must be **atomic with respect to the save cycle**: `save_now()` is called once, at the end of step 5, never between the earlier steps. If the app dies before that `save_now()` completes, the restored save is the pre-transition state with `_card_pending = true` (BurnoutSystem's existing persistence), and the Wypalenie card re-presents on boot — the player re-confirms and the whole sequence re-runs from the top. No partial-transition state is ever persisted.
- **If the app is killed after `era_transitioned` fires but before Challenge Selection is confirmed** *(narrowed per `/design-review`, 2026-07-13 second re-review — see Interactions' Save/Persistence entry: `save_now()`/`resume_autosave()` now run at step 5, before `era_transitioned` and Challenge Selection, not after the whole sequence)*: the era-flip itself is already durably saved (it completed and was persisted before `era_transitioned` fired), so this is no longer a mid-atomicity-window risk — it's an ordinary post-transition autosave gap, no different in kind from any other unsaved player action. On restore, the era is transitioned and challenge flags are whatever was confirmed — or none, since zero-challenge is a valid, safe default state. ChallengeSystem's own restore-from-flags reconstruction (its quick-spec Rule 3.3) handles this without new machinery.
- **If Choice B (Defer) is taken with Morale below `BURNOUT_DEFER_MORALE_COST`**: Morale clamps at 0 per the Final Burnout spec (survivable, not a death spiral) — restated here only to note META_BONUS is untouched by Defer; no grant, no read of path state.
- **If a save predates this system**: `era_count` defaults to 0, all `META_BONUS_total[type]` default to 0.0, no meta-persistent burnout flags exist — standard missing-key default pattern (same as `OnboardingGate`/`SettingsSystem`/Class Path migration). The player is treated as being in their first era, which is exactly true.
- **If `inject_priority_card()` is called while another priority card is already pending**: rejected (returns `false`/error, no queueing). Contract: at most one priority card in flight; today's only caller (BurnoutSystem) already guards with `_card_pending`, so a second concurrent injection indicates a caller bug, not a game state to support. Revisit only if a second forced-card mechanic ever ships.
- **If offline simulation runs with a nonzero `META_HATERS_RESIST_total`**: the resistance applies to the offline Haters growth (F3c's locked online+offline scope) using the value as-of-save-time — grants only ever happen in active play (Choice A is an active-play interaction), so the total cannot change during an offline window; there is no mid-simulation value ambiguity.
- **If `BASE_INCREMENT` or `META_BONUS_MAX` is misconfigured to 0 or negative in balance.json**: grants compute to ≤ 0 — clamp `bonus_increment` to `max(0.0, computed)` at grant time (a zero grant is safe; a negative grant would violate Core Rule 5's never-reduced guarantee). Log a config warning; do not crash.
- **If F3a's multiplicative chain produces a sub-1 result** *(added per `/design-review`, 2026-07-13)* — a hard Morale band (`Mult(M)=0.50`), a low-`base_reach` action, a near-floor `challenge_modifier` (`CHALLENGE_MODIFIER_FLOOR`), and zero accrued `META_REACH_MULT` (realistic for an early-era player who stacked a hard challenge before their first grant) can compute `final_reach < 0.5`, rounding to **0 Reach** for a completed action — a real reward of nothing, unaddressed by any existing rule. F3a now applies `max(1, round_half_up(...))` for any completed action (see F3a) — a completed action always grants at least 1 Reach, mirroring `META_HATERS_RESIST`'s existing "never fully zero a core resource flow" principle (DDR-0001 #2) by direct extension.

Too low: exploring all four paths barely matters, doesn't counter mono-path dominance. Too high: risks a large simultaneous jump across all four caps right when the fourth path is first tried |
| `META_CHALLENGE_SCALING_EXPONENT` | 0.5 | 0.3–0.5 *(narrowed from 0.3–1.0, `/design-review` 2026-07-13 re-review)* | Above 0.5 (no longer a settable value): a single stacked-challenge Tier-5 burnout can overshoot a type's cap by 3–9x in one grant. Below 0.3: challenge-stacking barely rewards, undermining ChallengeSystem's entire trade |
| `META_BONUS_MAX[type]` (per-type array) | `{0.50, 0.50, 0.40, 100.0}` *(sponsor_mult lowered from 0.60, see F2)* | see F2 rationale column | Reach/Sponsor caps too high: permanent inflation dwarfs era-local play. `META_HATERS_RESIST` above ~0.6: approaches zeroing a core resource flow (DDR-0001 #2 territory). Floor cap too high: era-start stops feeling like a reset |
| `era_start_defaults` (5 resources) | Cringe=0, Morale=100, Haters=0, Reach=0, Sponsors=0 (locked, Final Burnout §4.2) | fixed | Owned by the Burnout spec; F3d's floor overrides Sponsors only. Changing Morale=100 interacts with `BURNOUT_DEFER_MORALE_COST` — never tune independently |

**Knob interactions**: `BASE_INCREMENT` × `TIER_FLAT_BASE` × `META_CHALLENGE_SCALING_EXPONENT` × `META_BONUS_MAX` jointly set "eras to cap" — the single most important pacing number this system owns (target: a typical mixed-play player caps their first type in ~8–12 eras; validate in playtest). Tuning any one alone shifts it; economy-designer owns the joint pass (Open Questions).

**⚠️ Pacing values are illustrative, not final** *(added per `/design-review`, 2026-07-13)* — every default in this table, and every worked example / Acceptance Criterion numeric value derived from it, exists to make the *formulas and mechanics* verifiable now. The "8–12 eras to cap" target itself is explicitly unvalidated (Open Questions, BLOCKING-before-Alpha). Because `META_BONUS_total` is permanent and never reduced (Core Rule 5), retuning any cap downward after players have already exceeded the new value has no defined migration path — this GDD does not resolve that, and implementers should treat all numeric defaults here as subject to change before Alpha, not as locked balance truth. Acceptance Criteria that assert specific numbers (F1/F2/F3) are testing *formula correctness*, not *final balance* — they will need updated expected values, not new logic, when playtest data lands.

### META_BONUS Grant Magnitude (F1)

### Bonus Type Selection by Active Path (Core Rule 1/3)

- **GIVEN** Choice A resolves while each of the four paths is, in turn, active, **THEN** the grant targets `META_REACH_MULT` / `META_SPONSOR_MULT` / `META_HATERS_RESIST` / `META_SPONSOR_FLOOR` respectively — never a mismatched type. **[Logic — BLOCKING]**

### Transition Atomicity

- **GIVEN** the app is killed mid-sequence (after Choice A confirmed, before `save_now()`), **WHEN** the app restarts, **THEN** the restored state is the pre-transition state exactly (`era_count` NOT incremented, no META_BONUS granted, previous era's resources/affiliation intact) with `_card_pending=true`, and the Wypalenie card re-presents on boot. **[Integration — BLOCKING against a mocked `SaveSystem`]**
- **GIVEN** the player re-confirms Choice A after such a restore, **WHEN** the sequence re-runs, **THEN** it executes exactly once from the top — META_BONUS is granted exactly once total across both attempts, no partial-application artifacts survive. **[Integration — BLOCKING]**
- **GIVEN** the app is killed after `era_transitioned` fires but before Challenge Selection is confirmed, **WHEN** the app restarts, **THEN** the era is already transitioned (`save_now()` completed at step 5, before `era_transitioned` fired — see States and Transitions) and the challenge set is either empty (safe default) or whatever was already confirmed — never partially-selected. **[Integration — BLOCKING]**
- **GIVEN** the era-transition sequence (steps 1-5) has completed and `save_now()` has run, **WHEN** the app is killed at any point during Challenge Selection (step 7) before it is confirmed, **THEN** autosave suppression has already been lifted (per the narrowed suppression window, `/design-review` 2026-07-13 second re-review) — this is an ordinary post-transition autosave gap, not an atomicity violation; no unbounded suppression window exists across a player-paced screen. **[Integration — BLOCKING]** *New AC, second re-review — closes the mobile data-loss risk godot-specialist flagged in the original wider suppression window.*

### `inject_priority_card()` Contract (Core Rule 6)

- **GIVEN** no priority card is pending, **WHEN** `inject_priority_card("final_burnout")` is called, **THEN** it presents on the next available frame, bypassing pool selection, weighting, and cooldown entirely. **[Integration — BLOCKING]**
- **GIVEN** a priority card is pending, **WHEN** a normal pool-selected card would present, **THEN** presentation is blocked until the priority card resolves. **[Integration — BLOCKING]**
- **GIVEN** a priority card is pending, **WHEN** `inject_priority_card()` is called again with a different `card_id`, **THEN** the call is rejected (returns `false`/error), no queueing, the originally pending card remains sole. **[Logic — BLOCKING]**

### Misconfiguration Guard

- **GIVEN** `BASE_INCREMENT[META_REACH_MULT]` is misconfigured to `-0.02` (or `0`), **WHEN** F1 computes a Tier-3 grant, **THEN** it clamps to `max(0.0, computed)=0.0`, no exception, a config warning is logged. **[Logic — BLOCKING]**
- **GIVEN** such a clamped zero grant, **THEN** the running total is unchanged — Core Rule 5's never-reduced guarantee holds even under misconfiguration. **[Logic — BLOCKING]**

### Persistence — Save Migration

- **GIVEN** a save predates this system (no `prestige` key), **WHEN** `PrestigeSystem` initializes, **THEN** `era_count` defaults to `0`, all four `META_BONUS_total[type]` default to `0.0`, no meta-persistent burnout flags exist — same default-on-missing-key pattern as `OnboardingGate`/`SettingsSystem`/Class Path migration. **[Integration — BLOCKING]**
